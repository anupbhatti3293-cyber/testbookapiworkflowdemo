# Testbook API — Helm & kubectl Demo Cheat Sheet

## 1. Demo Architecture

```text
                    AWS EKS
                       |
              testbook-cluster
                       |
              +--------+--------+
              |                 |
            Node 1            Node 2
              |                 |
              +--------+--------+
                       |
                    Kubernetes
                       |
                       |
                      Helm
                       |
          +------------+-------------+
          |                          |
   deployment.yaml              service.yaml
          |
     values.yaml
          +
   values-dev.yaml
```

### Simple explanation

* **EKS** gives us the Kubernetes cluster.
* **Nodes** are the machines on which our application runs.
* **Kubernetes** manages our application containers.
* **Helm** packages and templates our Kubernetes configuration.
* **kubectl** lets us inspect and interact with Kubernetes.

---

# 2. Create the EKS Cluster

For this demo we are creating:

* Cluster: `testbook-cluster`
* Region: `eu-north-1`
* Worker nodes: `2`
* Instance type: `t3.small`

```bash
eksctl create cluster \
  --name testbook-cluster \
  --region eu-north-1 \
  --nodegroup-name testbook-nodes \
  --node-type t3.small \
  --nodes 2 \
  --nodes-min 2 \
  --nodes-max 2 \
  --managed
```

### Explain to students

> "For today's demo I am manually creating the Kubernetes infrastructure. In a professional environment, this infrastructure would normally be managed through Infrastructure as Code such as Terraform, CloudFormation or AWS CDK."

# HELM COMMANDS

# 6. What Is Helm?

Without Helm we might maintain Kubernetes files directly:

```text
deployment.yaml
service.yaml
```

With multiple environments we could end up duplicating them:

```text
DEV deployment.yaml
TEST deployment.yaml
PROD deployment.yaml
```

Helm allows us to create reusable templates:

```text
helm/
└── testbook-api/
    |
    ├── Chart.yaml
    ├── values.yaml
    ├── values-dev.yaml
    ├── values-test.yaml
    ├── values-prod.yaml
    |
    └── templates/
        ├── deployment.yaml
        └── service.yaml
```

Think:

```text
Template
   +
Environment Values
   =
Final Kubernetes Configuration
```

# 10. Render the Helm Templates Without Deploying

One of the BEST commands for explaining Helm:

```bash
helm template testbook-api \
  ./helm/testbook-api \
  -f ./helm/testbook-api/values-dev.yaml
```

### Purpose

This does NOT deploy anything.

It shows the final Kubernetes YAML generated by Helm.

Explain:

```text
deployment.yaml
      +
service.yaml
      +
values.yaml
      +
values-dev.yaml
      |
      v
     HELM
      |
      v
Final Kubernetes YAML
```

This is probably the most important Helm teaching command.

# 12. Deploy Testbook API Using Helm

```bash
helm upgrade --install testbook-api \
  ./helm/testbook-api \
  --namespace dev \
  -f ./helm/testbook-api/values-dev.yaml \
  --set image.repository=316255801172.dkr.ecr.eu-north-1.amazonaws.com/mybookapi \
  --set image.tag=demo \
  --wait
```

### Explain the command

```text
helm upgrade --install
```

means:

```text
Does Testbook API already exist?

        |
   +----+----+
   |         |
  NO        YES
   |         |
Install    Upgrade
```

This makes it very useful for CD pipelines.

```bash

```

```text

```

column.

Conceptually:

```text

```

Explain:

> "Kubernetes decides which worker machine should run each Pod."

Important:

# HELM UPGRADE DEMO

# 23. Change the Number of Replicas

Suppose `values-dev.yaml` currently contains:

```yaml
replicaCount: 1
```

Change it to:

```yaml
replicaCount: 2
```

Then:

```bash
helm upgrade testbook-api \
  ./helm/testbook-api \
  --namespace dev \
  -f ./helm/testbook-api/values-dev.yaml \
  --set image.tag=demo \
  --wait
```

Now:

```bash
kubectl get pods -n dev -o wide
```

Explain:

```text
values-dev.yaml

replicaCount: 2

        |
        v

helm upgrade

        |
        v

Kubernetes

   +----+----+
   |         |
   v         v
 Pod 1     Pod 2
```

This is a very good demonstration of why Helm is useful.

---

# 24. Override a Value Without Editing the File

You can also demonstrate:

```bash
helm upgrade testbook-api \
  ./helm/testbook-api \
  --namespace dev \
  -f ./helm/testbook-api/values-dev.yaml \
  --set replicaCount=4 \
  --set image.tag=demo \
  --wait
```

Explain:

> "`--set` allows a CI/CD pipeline to dynamically provide a value without manually editing the Helm file."

This is particularly useful for Docker image tags.

For example:

```bash
--set image.tag=a72bc91
```

# 32. Demonstrate Kubernetes Self-Healing

This is a great Kubernetes demonstration.

First:

```bash
kubectl get pods -n dev
```

Delete one Testbook Pod:

```bash
kubectl delete pod <POD_NAME> -n dev
```

Immediately:

```bash
kubectl get pods -n dev
```

Kubernetes creates another Pod.

Explain:

```text
Helm/Kubernetes desired configuration:

2 replicas


Before:

Pod 1
Pod 2


Delete Pod 1

Pod 2


Kubernetes notices:

"Wanted = 2
Actual = 1"

        |
        v

Creates replacement

        |
        v

New Pod
Pod 2
```

Important teaching point:

> "Helm defines/configures the desired Kubernetes application, but Kubernetes itself performs this Pod self-healing."

---

# 33. Manually Scale With kubectl

You can demonstrate:

```bash
kubectl scale deployment testbook-api \
  --replicas=3 \
  -n dev
```

Then:

```bash
kubectl get pods -n dev
```

This proves Kubernetes can scale without Helm.

But then explain:

> "For a managed deployment, we generally want our declared configuration to remain the source of truth rather than making random manual changes."

If Helm says:

```yaml
replicaCount: 2
```

but you manually change Kubernetes to:

```text
3
```

the configuration and actual cluster have diverged.

This becomes an excellent introduction to **GitOps and Argo CD**.

# The One Sentence to Remember

> **Helm manages how the Kubernetes application should be packaged, configured and released; kubectl lets us communicate with Kubernetes and inspect or operate what is actually running.**

Or even shorter:

```text
Helm
  =
Package / configure / release

kubectl
  =
Talk to / inspect / operate Kubernetes
```
